Scope-aware preliminary validation is pending under the linked fix plan; current legacy corridor checks still inspect the whole trace. Do not redesign IPOPT to make discrete choices.

## Corridor diagnostics and future-test review

Corridor checking remains enabled. Whether to keep it long term is undecided. The [bug-fix plan](CORRIDOR_CONSTRAINT_FIX_PLAN.md) separates completed instrumentation from pending behavior changes. The [Real11 exact audit](experiments/linkcraft11-opening/audit/CORRIDOR_FAILURES.md) contains a worked failure and diagram.

Rejected returned candidates persist diagnostics at `result.contactAttempts[i].candidateFilter.corridorAudit`; experiment reports may nest the result under a run or evaluation. Record version1 contains:

- `corridorHash`, `corridor` and `gates`: the selected cells, source/helper points, projected rectangles and expected route signature. These permit later identification of artificial route restrictions.
- `failure`: either the first failing zero-based input, Y/X/Z phase, exact segment endpoints/state references and coverage tolerance, or the expected/actual crossing token and crossing sequence. State t is pre-input; input t produces state t+1.
- `scope`: horizon, partial-signature mode and the actual projection scope. Currently `modeledInteractionScope=unspecified` explicitly exposes the missing scope contract. `partialSignature=true` does not switch off future obstacle projection checks.
- `plan`, `candidate`, `vertical`: supplied compiled walls/contacts, returned trajectory/facings/velocity/friction, and the scalar vertical model needed for independent scene replay.
- `selectedPassages`, `selectedHits`, `extraRows`, `numericalRequests`: the selected discrete geometry branch and its numerical problem hashes/status/allocation. `repairAlternatives` records proposed additional rows, not rows already supplied to this solve.
- `physicalReplay`: `not_run` means the corridor rejected the candidate before shared scene validation; `not_configured` means there was no supplied scene. Neither means the trajectory physically passed or failed.

These records describe final returned branch candidates. The adapter's `corridorAudits`, `corridorProjectionRejections` and `corridorSignatureRejections` also count intermediate callback audits. Use `numericalRequests` and worker counters to count solver requests rather than treating every audit as a new call. Existing accepted corridor verdicts and subsequent `geometryCheck` records remain available through the normal per-branch logs. Logging adds no solver/replay calls and does not change the current rejection or repair policy.

To investigate a rejected record, retain the experiment's original fixture/declared scene and replay the saved data with the existing bridge, separately from the timed search:

```python
physical = check_geometry(scene['collisionScene'], audit['plan'], audit['candidate'],
                          audit['vertical'], compiler, 3)
```

Here `audit` is the saved corridorAudit, and `compiler` is an existing JavaCompiler opened with the standalone compiler manifest. Save the resulting verdict separately. Classify the evidence as route-only rejection with passing physical replay, physical collision from missing constraints, numerical/model discrepancy, or deliberately omitted future interaction in a preliminary model. Preserve failed traces as well as accepted witnesses. In particular, a skipped scene check cannot support an assertion of physical collision. Compare route-only rejects against retained alternatives before deciding whether the corridor policy helps or overrestricts the solve.
