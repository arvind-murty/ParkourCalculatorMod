## Why the optimized 400-input replay is unknown, 2026-10-26

Terminology clarification: in this experiment IPOPT does not discover collisions. The request prescribes wall-hit ticks/planes, and its model applies blocked-axis velocity resets and ladder behavior. The missing consequence is wall-triggered sprint cancellation and the resulting carried air-acceleration change. This is an incomplete physical model/coefficient compilation in our pipeline; IPOPT solves the supplied model, while exact replay exposes its inconsistency. The new scene-based replay can discover contacts when geometry is supplied, but the 400-input diagnostic used declared contacts.

The 400-input candidate still matches the current ladder fixture's physical problem hash. Independently running the scalar continuous validator accepts it with zero violation and objective 691.5810209171883. The unknown verdict belongs to subsequent exact replay/angle realization, whose five-second repair budget expired, not to an IPOPT convergence failure or an infeasibility certificate.

The primary failure is an inconsistent sprint assumption in the compiled optimization coefficients, not merely float angle realization. Every airborne coefficient through the first ladder uses magnitude approximately 0.026. FORCE_45 in the native compiler authors sprint=true, and its `healWallHitSprint` policy is designed to restore sprint after hits the native solver is expected to avoid. This policy does not fit the standalone fixed-contact problem, which deliberately requires those wall hits while climbing.

Observed exact timeline from the realized candidate:

- State 136 has the first ladder/wall hit. Sprint is still true on that completed movement.
- Processing input 136 observes the preceding horizontal collision and cancels sprint. State 137 records sprint=false. Legacy air acceleration uses a carried movement factor, so the lower approximately 0.020 acceleration takes effect starting input 137. The first capped ticks mask some of the discrepancy; later ladder movement diverges.
- At state 152, exact X is 0.174005654 blocks above the continuous candidate. By state 189 the difference is 0.269037127 blocks.
- The required negative-X wall at state 190 is at X=736.4250000119209. The exact uncorrected path reaches only X=736.6725760013390, missing by 0.247575989418 blocks. It actually reaches that declared wall at state 193, three states late. This denies the expected earlier climb carry and subsequently invalidates the remaining declared vertical contacts. The large final Y error is a cascade after leaving the declared event schedule, not evidence that every earlier movement formula is wrong or a prediction from a complete scene.

A diagnostic counterfactual changed only the local replay's incoming air-sprint factor to always use sprint acceleration, matching the optimization's assumption. All declared contact reach failures disappeared, the state-190 wall hit occurred correctly, and the maximum overall position difference from the continuous path fell to 0.00119029446 blocks. Remaining original-row violation was about 0.000602279 at Z@98hi. Thus ordinary float/sine-table realization still needs correction, but it is separate from the much larger sprint-model discrepancy. The counterfactual was confined to temporary probe code and is not a proposed physics change.

Correct next implementation: compile/regenerate the fixed-contact request's acceleration coefficients using the actual wall-aware sprint/input state and legacy movement-factor carry, solve that physically consistent problem, then use angle realization for the smaller residual differences. ## Modeling findings

Independent scalar replay determines acceptance from returned facings; worker success and returned state values are not trusted. Automatic inertia and conditional wall clipping must satisfy every requested constraint at 1e-7 tolerance. A missed plane cannot reset velocity even if the miss is below that tolerance. Unsuccessful local search is unknown, not certified infeasibility.

Retaining the best valid incumbent and polishing its actual inertia pattern fixes a material warm-start regression. A previous no-inertia path can seed a subsequent inertial/ladder solve, but it must pass the changed model before becoming an incumbent. A distinct fallback shares the total budget.

Ladder caps apply independently to X/Z after acceleration and inertia, before collision reach and friction. The smooth NLP fixes free/positive/negative cap branches and tries bounded neighboring regimes. An analytic regression confirms that branch changes recover an optimum missed by the initial fixed branch. Climbing uses ladder occupancy and the previous movement's horizontal collision; its upward movement occurs on the following tick. Stored vertical carry and collision state survive span seams.

Real11 ladder occupancy is prescribed from captured climb signatures and climb-proven cells, including states 189 and 361 without a climb signature. Through 400 inputs the ranges are 136-152, 189-193, 356-362 and 395-399; final state 400 is also on a ladder. Vertical replay includes prescribed floor, ceiling and step events. Step-ups during jumps and landings explain the initial Y mismatch. General geometry discovery, ladder membership checks against a changed path and full world collision validation remain outside this model.

The copied 200/400 fixtures retain all original compiled constraints and horizontal contacts. Their ladder/Y copies have 22/34 ladder input ticks, 50/81 vertical contacts and 8/9 steps respectively. Captured Y positions, stored vertical velocities and ground states replay exactly. The source capture file SHA-256 is af5d2d1bc6e0ab466f1b6cf309f3a26e76e4a63765ac8b15ff02fb4ad55d28bf. ### 1. The reusable replay path

SimulationRunner.simulate resets the loader Simulator, snapshots state 0, applies each InputRow and records state/checkpoint t+1. simulateFrom restores checkpoint t and replays its tail. LazyEntitySimulator applies the actual per-row keys/effects, locked absolute float yaw or relative float yaw, then ticks the loader entity. ForgeSimulator/FabricSimulator bind that entity to an available Minecraft world and run the corresponding MC update/tick. Their SimulatorEntity implementations delegate collision movement to superclass move/moveEntity and travel, while sampling medium/friction and maintaining sprint/input state.

This is the right source for actual movement/collision validation. It already has ground/wall/ladder/step behavior via Minecraft, unlike the collision-free ExactJumpModel. Lifting the core driver is straightforward, but the loader entity still needs the correct Minecraft runtime and world. It cannot become a plain standalone Python replay merely by copying the Java source. A headless world/runtime or exported-scene physics engine would be a separate project. A mod-hosted scratch replay service is the smallest route to real Minecraft validation.

The visible TAS playback path is separate: PlaybackController plus loader PlaybackBridge drives the real player in supported singleplayer or a client replica in multiplayer. It handles tick scheduling, pause, warmup, effects and camera interpolation. It should be an eventual end-user playback cross-check, not the inner search oracle that repeatedly teleports or drives the real player. Fast simulation is not limited to real-time 20 Hz playback.

Fresh simulator starts perform two neutral settle ticks, then restore supplied position/velocity and optional StartResumeState. PlaybackController also distinguishes a fresh start from an already settled carried checkpoint. Preserve these semantics rather than adding an extra neutral tick to a solved window. Full in-memory checkpoints capture more fields than portable StartResumeState: for example legacy landMovementFactor, width/height and fallDistance are in entity checkpoints. An independently saved mid-route window therefore needs verified resume equivalence; initial implementation can preserve the original TAS prefix.

### 2. Deterministic yaw conversion is not intelligent realization

JumpPhysicsInputs.toGameFacingsInto mirrors how Apply writes relative float deltas and the game accumulates them, or casts locked rows to absolute floats. It is deterministic realization of row semantics, not constraint-aware correction of the continuous path. AngleSolverEngine.writeYawRows and ApplyYawRowsTest pin the same chain. Simply casting every continuous absolute angle to float can disagree with relative-row accumulation.

PlaybackController deliberately preserves raw physics yaw separately from the display's shortest-turn interpolation. Its code notes that 45 and -315 need not select identical sine buckets. Do not normalize all exported physical yaws modulo 360 as an assumed identity, and do not validate only the displayed camera angles.

FacingLattice provides exact movement sine/cosine indices, joint-cell IDs/intervals and nearby cell representatives. Legacy movement and sprint-jump boost use different radian casts, so a jump cell can depend on four indices, not just one ideal angle bucket. It supports a separate 26.x index path as well; version-specific candidate enumeration must be preserved. Neighbor candidates should be deduplicated by realized joint cells and checked against original facing/relative-facing constraints.

Within-cell representative choice still matters for original F/dF restrictions and for subsequent relative-yaw accumulation. Cell deduplication is not permission to discard the feasible part of a cell because one arbitrary representative misses a facing pin. Preserve/intersect cell intervals with facing restrictions and verify the actual accumulated sequence when realizing representatives.

CertifiedBnb.realizeCombo is a useful precise serialization reference: it tries nearby absolute values in ULP steps until float delta accumulation lands on the chosen joint-cell identity, rather than assuming a selected float representative can always be written back unchanged. It is private certification code; use it as a pattern without changing certified B&B or importing its search machinery into replay. Absolute locked rows can remove delta-accumulation error in a newly generated TAS, but they do not remove sine-table/float-physics drift from the continuous solution. A patch to an existing template must respect the chosen row-lock policy.
